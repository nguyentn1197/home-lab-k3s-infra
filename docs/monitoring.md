# Monitoring Stack

Metrics and logs for the homelab cluster **and** for external machines (other docker hosts, standalone VMs). Built from the most common community charts: **kube-prometheus-stack** (Prometheus + Grafana + Alertmanager), **Loki** (logs), and **Grafana Alloy** (log collection).

## Design Goals

The stack is deliberately **not highly available** — every stateful component runs a single replica — but it is **recoverable with a restart**: all state (Prometheus TSDB, Loki chunks/index, Grafana dashboards) lives on Longhorn PVCs (2 storage replicas). If a pod or node dies, Kubernetes reschedules the pod, Longhorn reattaches the volume, and the stack resumes with all history intact. The trade-off is a few minutes of blind spot during a restart, which is acceptable for a homelab.

## Components

| Component | Chart / repo | Mode | State |
|-----------|-------------|------|-------|
| Prometheus, Grafana, Alertmanager, node-exporter, kube-state-metrics | `kube-prometheus-stack` `86.x` (prometheus-community) | 1 replica each | Prometheus 50Gi PVC (15d / 45GB retention), Alertmanager 2Gi, Grafana 2Gi |
| Loki | `loki` `17.x` (**grafana-community** — the OSS chart moved there in Mar 2026) | Monolithic single binary | 30Gi PVC, filesystem storage, 30d retention via compactor |
| Alloy | `alloy` `1.x` (grafana) | DaemonSet, clustering enabled | stateless |

All run in the `monitoring` namespace. Manifests:

- `infrastructure/controllers/kube-prometheus-stack.yaml`
- `infrastructure/controllers/loki.yaml`
- `infrastructure/controllers/alloy.yaml`
- `infrastructure/configs/monitoring-httproute.yaml` (Grafana/Prometheus/Loki routes)
- `infrastructure/configs/monitoring-external-scrape.yaml` (external metric targets)

Chart version ranges follow the repo convention; confirm the current majors before first deploy with `helm search repo <repo>/<chart> --versions` if a long time has passed.

## How Data Flows

### In-cluster metrics (works out of the box)

kube-prometheus-stack deploys the Prometheus Operator plus node-exporter (DaemonSet, tolerates the master taint) and kube-state-metrics. Kubelet/cadvisor and apiserver are scraped automatically, and the chart ships the standard Grafana dashboards and alert rules.

K3s embeds controller-manager, scheduler, kube-proxy, and etcd and doesn't expose their metrics endpoints by default, so those scrapes are disabled in the values to avoid permanent `TargetDown` alerts. To enable them later, add the relevant `--kube-controller-manager-arg=bind-address=0.0.0.0` / `--etcd-expose-metrics` flags to the K3s install in Ansible and re-enable the corresponding chart values.

The Prometheus spec sets all the `*SelectorNilUsesHelmValues: false` flags, meaning Prometheus picks up **any** `ServiceMonitor`, `PodMonitor`, `Probe`, `PrometheusRule`, or `ScrapeConfig` committed anywhere in the cluster — no labels required. Apps that expose metrics just need a `ServiceMonitor` next to their manifests in `apps/base/`.

### In-cluster logs (works out of the box)

Alloy runs as a clustered DaemonSet and tails every pod's logs through the kubelet API (`loki.source.kubernetes`), labels them with `namespace`, `pod`, `container`, `app`, `node`, and `cluster=homelab`, and pushes to `loki-gateway`. Clustering shards targets across members so logs are not duplicated. Loki is queryable in Grafana via the pre-provisioned `Loki` datasource.

### External metrics (cadvisor / node_exporter on other machines)

Run the exporter on the external machine, then add a target to `infrastructure/configs/monitoring-external-scrape.yaml`:

1. **Docker hosts**: run the cAdvisor container (command in the file's header comment), exposes `:8080/metrics` with per-container CPU/mem/net/disk.
2. **Plain VMs**: run node_exporter (`:9100/metrics`) as a systemd service or container.
3. Add the `IP:port` to the matching `ScrapeConfig` (`external-cadvisor` / `external-node`) with a friendly `host` label, commit, push.

Because the ScrapeConfig CRD is just another Git-managed resource, each new machine is a 3-line diff. The file currently contains **placeholder IPs (`10.10.0.50`) — edit them to real hosts** or the targets will show as down.

Ensure the machines' firewalls allow the cluster nodes (`10.10.30.0/24`) to reach the exporter ports.

### External logs (docker containers / VM system logs)

External machines **push** to Loki through the Gateway API route `http://loki.kube.local.tnndev.com/loki/api/v1/push`. Install Alloy on the machine (deb/rpm package or the `grafana/alloy` docker image) with a config like:

```alloy
// Send everything to the homelab Loki
loki.write "homelab" {
  endpoint {
    url = "http://loki.kube.local.tnndev.com/loki/api/v1/push"
  }
  external_labels = {
    host = "my-vm-name",   // set per machine
  }
}

// VM system logs (systemd journal)
loki.source.journal "system" {
  forward_to = [loki.write.homelab.receiver]
  labels     = { job = "systemd-journal" }
}
```

VMs ship their journal via a native Alloy install; docker hosts ship container logs via a containerized Alloy (config in `docs/examples/external-monitoring/config.alloy`). (Promtail works too but is deprecated in favor of Alloy.)

Ready-made templates live in `docs/examples/external-monitoring/`:

- `docker-compose.yml` + `config.alloy` — for docker hosts: cAdvisor + node_exporter (metrics) and a containerized Alloy that ships all container logs. Start with `HOST_LABEL=my-docker-host docker compose up -d`.
- `setup-alloy.sh` — for VMs: installs Alloy via apt and ships the systemd journal. Run it on docker hosts too if you also want the host's journal.

## Recovery Model

| Failure | What happens |
|---------|--------------|
| Prometheus/Loki/Grafana pod crash | Pod restarts on the same PVC; data intact, gap of seconds–minutes |
| Worker node dies | Pod reschedules to another worker; Longhorn reattaches the replica volume; gap of a few minutes |
| Alloy pod dies | DaemonSet restarts it; cluster re-shards tail targets; kubelet log position may replay/skip a small window |
| Full cluster restart | Everything comes back from PVCs in Flux dependency order; external pushers (Alloy on VMs) buffer & retry while Loki is down |
| PVC lost | Metrics/logs history is gone but the stack redeploys cleanly from Git — monitoring data is treated as expendable; Longhorn recurring backups can be added to the PVCs if history matters |

## Deliberate Simplifications

- **No HA**: single Prometheus, single Loki binary, single Grafana. Restart-recoverable per above.
- **Loki filesystem storage** instead of S3/MinIO: fewer moving parts; the PVC is the storage. If log volume grows, switch `object_store` to S3/MinIO later (the schema config already uses TSDB v13, so only the storage section changes).
- **Loki caches and canary disabled**: the chart's memcached statefulsets default to ~8Gi RAM each — overkill here.
- **`auth_enabled: false`** on Loki: single tenant, LAN-only exposure. The HTTPRoute only forwards `/loki/api` paths.
- **No Kubernetes events collection yet**: `loki.source.kubernetes_events` doesn't shard across a clustered DaemonSet (would duplicate). Add it later as a separate single-replica Alloy if wanted.
- **Alertmanager receivers unconfigured**: alerts fire but go nowhere; add a receiver (e.g. ntfy/Telegram/email) under `alertmanager.config` when ready.

## Adding Things Later

- **New in-cluster app metrics** → commit a `ServiceMonitor` in the app's namespace.
- **New external machine** → add targets to `monitoring-external-scrape.yaml`; install Alloy on it for logs.
- **Dashboards** → import in Grafana UI (persisted on the PVC), or commit ConfigMaps labeled `grafana_dashboard: "1"` for GitOps-managed dashboards (sidecar is enabled by default in the chart).
- **Alert routes** → `alertmanager.config` in the HelmRelease values.
